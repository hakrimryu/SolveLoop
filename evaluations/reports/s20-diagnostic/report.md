# S20 LF再診断（保留評価外）

S20の既存文・既存シナリオを使った原因確認であり、新規評価質問や品質スコアへ加算しない。準備済みの`solveloop-demo`を変更せず、別の評価DBへ最終LF入力を複製した。manifest `dcfb4b5caec143bd5b9eb93875bf1531c8702e20a67ad827de66bc2882ee8c99`、製品/モデル/digest/profile/prompt/thresholdは[基準線](../baseline-v1/report.md)と同じ。

実埋め込み→同一9件候補→3回の承認前判定→同一3解決根拠からの3回生成→S20で編集された本文と同じ文書を実準備・API承認→3回の再判定を実行した。今回のAPI承認は合成評価操作であり、利用者の下書き品質レビューを意味しない。

| 回 | 承認前 covered / uncovered / unknown / 未分析 | 承認後 covered / uncovered / unknown / 未分析 |
| --- | --- | --- |
| 1 | 0 / 9 / 0 / 0 | **4 / 5 / 0 / 0** |
| 2 | 0 / 9 / 0 / 0 | **4 / 4 / 1 / 0** |
| 3 | 0 / 9 / 0 / 0 | **3 / 4 / 2 / 0** |

承認後2回目のunknown1と3回目のunknownのうち1は**AI_INVALID_OUTPUT**。番号付き原文の手順を引用する際、モデルが「1.」「2.」等を除いた文字列を連結し、原文の連続引用でなくなった。製品は初回と形式修正後の両方を拒否した。意味が似ていても、引用照合に失敗した出力をcovered/uncoveredへ振り替えない。3回目のもう1件は**AI_UNAVAILABLE**。

同じ問い合わせと承認文書で、モデルがさらに本人確認/失効/再発行/連絡方法の詳細を要求してuncoveredとする現象は残った。S20の過去ブラウザ5/9と最終LF HTTP3/9の差を「改善」や固定した性能値として解釈できない。今回も3回の結果が異なり、通信・出力検証の失敗が混在している。APIはASGI経由であり、過去のブラウザ/TCP HTTPとの完全同条件比較ではない。

## S17/S20の下書き問題

3回とも同じ8個のstepsと空のcautionsを返した。旧登録の無効化・再発行・新端末登録・接続確認を複数の解決原文から別表現で繰り返している。完全に同じ文字列の重複ではないため、製品の重複文字列検査は通る。本人確認前の再発行禁止は原本にあるが抽出されなかった。

これは新規10種で注意欄が空だった結果と整合する。一方、新規の複数根拠3種では操作の重複が出なかったため、重複しないことを一般保証していない。[派生比較値](summary.json)に3回のtrace/hashと初回の必要な抜粋を残した。利用者のレビューは未実施。

## 再現と制約

[実行案内](../../README.md)の専用resetとdiagnose_s20.py、summarize_s20.pyを使用する。初回の診断準備は評価resetの検索状態singleton復元漏れで停止した。品質試行前の準備失敗であり、その記録を残したまま評価器だけを修正、新規結果先v2で実行した。

S20の27件/phaseという集計は9個の同一問い合わせを3回見た値であり、独立した27問ではない。対象候補をシナリオmetadataで選択しているが、製品の候補計算や判定へ正解を渡していない。初期承認15文書は合成過去記録、今回追加したMFA文書は隔離評価操作。原本DB・準備済みS20状態・ビルド・実env・既存backupの保全結果は内部記録を参照し、個人環境・dump・全API/Ollama応答はGitへ入れない。
